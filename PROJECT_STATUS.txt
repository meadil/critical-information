1. THE GOAL
-----------
Build a system that extracts "critical information" from raw sources (books,
podcasts, blogs, interviews) — not fluff, not everything that "sounds
important," but information that is specific and actionable relative to a
problem.

Key distinction driving the whole design:
  - Standard information = relevant context, not decisive
  - Critical information  = directly solves the problem at hand
  - Faulty information    = wrong or unverified, but looks legitimate

Two separate modes, deliberately kept apart:
  MODE B (what we're building right now): no target problem yet. Ingest
    everything from books/podcasts/blogs into a knowledge base. Don't try
    to judge "importance" at this stage — that's impossible without a
    problem to judge against. Just atomize (break into single-idea claims)
    and tag with metadata (source, claim type, topic, verifiability). This
    doubles as problem-discovery research: claims tagged as "pain_point"
    are signal for what problems actually exist in the niche (SaaS).

  MODE A (future, not built yet): once a specific problem is chosen, query
    the knowledge base (semantic search + tag filter) to pull a narrow
    candidate set, THEN apply relevance/specificity/verifiability scoring
    against that specific problem, then synthesize into an ordered
    methodology. This is cheap because it's a query over pre-processed
    data, not a re-read of every source.

Niche: SaaS. Still in the research/problem-discovery phase (Mode B), not
yet at Mode A.


2. THE END GOAL (full automation vision)
-----------------------------------------
OpenCode (local, free models) acts as the AGENT. The user just chats with
it normally ("here's a new podcast transcript, process it") and it decides
which tool to call — no separate "agent brain" needed elsewhere.

n8n acts as the TOOLBOX. One n8n workflow with one MCP Server Trigger node
exposes multiple tool nodes (HTTP Request Tool nodes calling a local
FastAPI server). OpenCode is configured with n8n's MCP endpoint as an MCP
server, so it can call these tools autonomously.

3. ARCHITECTURE OVERVIEW
--------------------------
Pipeline 1 (ingestion — THIS IS WHAT WE'VE BEEN BUILDING):
  Raw sources -> Conversion (PDF/audio/web -> text) -> Atomization
  (break into atomic claims, no judgment) -> Tagging (claim type, topic,
  verifiability) -> Storage (Supabase, with dedup/corroboration counting)

Pipeline 2 (retrieval/synthesis — NOT STARTED YET):
  Knowledge base -> Define problem -> Retrieve (semantic + tag filter) ->
  Problem-relative filter (relevance/specificity/verifiability scoring) ->
  Synthesis (ordered methodology)

Tool stack locked in:
  - PDF extraction: PyMuPDF
  - Audio/video: youtube-transcript-api (captions) -> faster-whisper (fallback)
  - Web scraping: Trafilatura
  - Atomize/tag: OpenCode (local models — Muse Spark for atomize, Nemotron
    for tag/score, since tagging needs more judgment)
  - Dedup: sentence-transformers embeddings + cosine similarity via
    Supabase pgvector
  - Storage: Supabase (Postgres + pgvector), project named "Critical
    Information"
  - Review checkpoint: Notion (human review of tagged claims before trust).
    Model settled 2026-09-29: Notion is the REVIEW INBOX, Supabase is the
    TRUSTED STORE.
      Notion  : holds only rows still awaiting a decision. Approved/rejected
                rows are removed once handled, so the inbox stays short.
      Supabase: holds only approved claims. rejected / needs_research are
                deleted. pending claims remain in both until decided.
    Access is via the Notion REST API directly (not the Notion MCP server) --
    this is a fixed bulk push/pull, not conversational work, so a deterministic
    script beats an improvising tool. The notion MCP entry stays in the global
    opencode config for the user's other project.
  - Orchestration glue: local FastAPI server (toolbox_api.py) wrapping all
    the Python scripts as HTTP endpoints
  - Agent/automation layer: OpenCode + n8n via MCP (see section 2)
